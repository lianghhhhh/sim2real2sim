# car_loc_fusion — 方法五: 把現有的所有感測器結合起來

```
高頻 60~200 Hz   /imu + /joint_states ──> 遞推 (7 維 EKF)  ─┐  連續、不會斷
                                                            ├─> /fusion_loc/odom
低頻 10~30 Hz    /camera_loc/odom (相機, 延遲 80 ms) ──┐    │   /fusion_loc/pose
                 /lidar_loc/odom  (LiDAR 對地圖)     ─┴────┘   TF map->base_link
                 絕對量測: 不漂、能自己找到自己, 但會斷
```

前四條路線是**互不相干**的 —— 那是為了讓它們能拿同一趟資料公平比較。
這一條是**把它們結合起來**的那一個。

| | 位置 RMS | yaw | 需要起點 | 會斷嗎 |
| --- | --- | --- | --- | --- |
| 只有相機 (60 Hz 拿最新一則) | 5.42 cm | 15~22° | 不用 | **會** |
| 只有 LiDAR (同上) | 6.97 cm | 2.9° | 不用 | **會** |
| 只有航位推算 (IMU+輪速) | 7.55 cm 且**持續長大** | 0.07° | **要** | 不會 |
| **融合** | **1.35 cm** | 0.03° | **不用** | 不會 |

(離線 bench, `test/test_fusion.py [A]`。「拿最新一則」是 60 Hz 的下游 —— TF、nav、
控制迴路 —— 真正感受到的誤差, 它包含**延遲**與**空窗**, 所以比那條路自己報的
精度差。融合把兩者都補掉。)

---

## 為什麼融合會比每一個來源都準

不是因為「多幾個感測器就比較好」, 是因為**兩類方法壞的方式不一樣**:

| | 絕對定位 (相機 / LiDAR) | 航位推算 (IMU + 輪速) |
| --- | --- | --- |
| 誤差 vs 時間 | 平的 | **單調長大** |
| 輸出會斷嗎 | **會** (遮蔽、幾何退化、追丟) | 不會 |
| 頻率 | 10~30 Hz | 60~200 Hz |
| 需要初始位姿 | 不用 | **要** |
| 短時間內 (< 0.1 s) 的相對運動 | 差 (量測雜訊主導) | **好** |

融合拿的正是彼此的長處: **高頻由遞推撐著, 絕對量測只負責把漂移按住。**
兩則相機 pose 之間的 33 ms 裡, 遞推比「上一則 pose 放著不動」準得多; 而遞推
一小時之後會漂到哪裡, 由絕對量測決定 —— 不由遞推決定。

這也正是 [report.md](../../report.md) §1 診斷舊路線失敗的原因: `wildbot` 實體車
的 AMCL + robot_localization 架構有輪速計提供最底下那一層, 而舊的模擬車沒有,
於是拿 ICP 自己疊了一個**沒有絕對參考**的里程計。這個 package 把那一層補起來。

## 用法

```bash
# 一鍵: 相機 + LiDAR + 融合一起開 (launch 會把前兩條的 publish_tf 關掉)
ros2 launch car_loc_fusion fusion_loc.launch.py
ros2 launch car_loc_fusion fusion_loc.launch.py evaluate:=true

# A/B
ros2 launch car_loc_fusion fusion_loc.launch.py camera:=false   # 少一個來源
ros2 launch car_loc_fusion fusion_loc.launch.py rewind:=false   # 關掉延遲補償

# 真車 (6 軸 IMU)
ros2 launch car_loc_fusion fusion_loc.launch.py use_sim_time:=false \
    imu_topic:=/imu/data gravity_mode:=complementary yaw_source:=gyro \
    sigma_acc:=0.35
```

跑之前三件事: **LiDAR 那條要先有地圖**、**相機那條要有 YOLO 模型**、
**開始前讓車子停著一秒** (開機靜止校正)。

> **不需要 `initial_pose`。** 第一則絕對量測就是起點。這是相對於 `car_loc_imu` /
> `car_loc_wheel` 的一個實質差別 —— 那兩條沒對到出生點的話整段差一個常數平移,
> 看起來像超大漂移。真的要在沒有絕對量測的情況下跑才用
> `wait_for_absolute:=false` + `initial_pose`。

## 這個 package 直接 import car_loc_wheel

遞推核心用的是 `car_loc_wheel.wheel_ins.WheelIns`, 沒有抄第二份。那 700 行裡有
打滑的三道防線、輪速的逃生口、零加速度的前提檢查, 每一項都是拿真資料調出來的
—— **同一段程式碼只能有一份**, 不然兩邊的參數會慢慢分岔, 而分岔的那一天不會有
人發現。`config/fusion_loc.yaml` 的遞推段因此必須跟 `wheel_loc.yaml` 保持一致。

「四條路線互不相干」的規則對這一條不適用: 它就是那個結合的節點。

**但它訂閱的是相機與 LiDAR 的 topic, 不是它們的內部狀態** (鬆耦合)。
緊耦合 (把雷射點雲與 YOLO 像素直接放進同一個濾波器) 理論上更準, 但:

1. **沒辦法單獨評估任何一種感測器了** —— 四條獨立路線是這個 repo 的資產。
2. **失效模式會直接傳染。** LiDAR 鎖到 180 度時, 鬆耦合看到的是「一則位置差
   10 公尺的 pose」, 一道閘門就擋掉了; 緊耦合看到的是幾百個點的殘差同時變小
   (它真的收斂到那個對稱解), 沒有東西擋得住。

代價是每一條路的輸出都已經被平滑過一次, 量測不再獨立 —— 見下面 [G]。

## [B] 最重要的一件事: 絕對量測的時戳是**過去**的

`car_loc_camera` 量到的延遲是 **79.5 ms** (曝光 + 傳輸 + YOLO 推論), 而且它很
誠實 —— 把時戳往回填成影像時刻。所以收到的那一則 pose 說的是「80 ms 前車子在
哪」。**把它當成「現在」直接更新, 等於灌一個 `v x Δt` 的位置誤差進去**, 方向
跟著車頭轉, 平均不掉:

| 車速 | 倒帶重放 | 不倒帶 | 差 | 理論 v x delay |
| --- | --- | --- | --- | --- |
| 0.6 m/s | **1.39 cm** | 5.24 cm | 3.9 cm | 4.8 cm |
| 1.8 m/s | **2.65 cm** | 15.62 cm | 13.0 cm | 14.3 cm |
| 3.0 m/s | **4.17 cm** | 27.11 cm | 22.9 cm | 23.8 cm |

**差距跟 `v x delay` 對得上** —— 這不是調參能解決的, 是時間軸的問題。
3 m/s 時不做補償的融合 (27 cm) 比只用相機 (5.4 cm) **還糟**:
> **融合做得不對, 比不融合還糟。**

做法是**倒帶重放** (rewind / fixed-lag re-linearization), 見 `fusion_ekf.py`:

1. 保留最近 `rewind_horizon` 秒的 IMU 輸入與狀態快照
2. 收到時戳 `t_m` 的 pose 時, 倒回 `t_m` 之前最近的一個快照
3. 用那一步的輸入 ZOH 遞推到 `t_m`, 在**正確的時刻**更新
4. 把 `t_m` 之後的每一步照原順序重放

第 4 步要連**期間已經套用過的其他絕對量測**一起重放: 相機 (30 Hz, 延遲 80 ms)
與 LiDAR (10 Hz, 延遲較小) 的**到達順序跟時戳順序不一樣**, 倒帶會跨過已經套用
的 LiDAR 更新, 不重放的話那次更新就憑空消失。

> **踩過的坑: 重放必須重現當初的決定, 不可以重新判閘門。**
> 原本重放時會重新算 NIS, 於是逃生口好不容易強制吃進去的那次修正, 在下一則
> 量測觸發倒帶時又被判成離群值丟掉 —— 修正被無聲地洗掉。症狀非常難看:
> **綁架之後永遠回不來, 但 `forced` 計數一直在增加。**

成本: 每則絕對量測要重跑 `horizon x IMU 頻率` 步 (0.4 s x 60 Hz = 24 步)。
40 Hz 的絕對量測 -> 每秒約 1000 次 7x7 遞推, Python 裡也還好。

### [H] 來源的時鐘 —— 2026-09-10 那一輪踩到的真問題

第一次拿真的 Isaac 資料跑融合, 結果是**整段凍結在起點**: 車子跑了 60 m,
`fus_` 的位置變動總量只有 0.17 m, 而濾波器自己報的 sigma 是 **0.42 mm**
(它非常確定自己停在原地)。

原因不是融合的參數, 是**時鐘**:

    /rgb 的 header.stamp 比 /imu、/odom、/scan 早 625.55 秒 (std 只有 10 ms)

`car_loc_camera` 忠實地把影像時戳傳下去, 所以 `/camera_loc/odom` 也整段偏 625 秒。
接下來發生的事一件比一件難看:

1. 時戳在「未來」-> `lag = ins.t - m.t` 是負的 -> **延遲補償整段被跳過**
2. 緩衝區的過期判斷 `now - t > horizon` 永遠是負的 -> **量測永遠不會被丟掉**
3. 每次倒帶重放都把累積的整段歷史再套用一次 -> 同一筆資料被算了幾百次
4. P 被壓垮 -> 之後所有量測都被卡方閘門擋掉 -> **估計凍結**

離線注入同樣的偏移 (`test/test_fusion.py [H]`):

| 相機時戳偏移 | 有時鐘偵測 | 關掉偵測 | sigma (關掉時) | `abs_log` 殘留 |
| --- | --- | --- | --- | --- |
| 0 s | 1.35 cm | 1.35 cm | 13.13 mm | 14 |
| 0.5 s | **4.08 cm** | 19.33 cm | 33.93 mm | 0 |
| **625.55 s** | **7.73 cm** | **112.26 cm** | 7.61 mm | 267 |

修法有兩層:

**(a) 每個來源自己量一個時鐘偏移** (`sources.py`): 前 20 筆量
`median(量測時戳 - 濾波器時刻)`, 符合任一條件就鎖定並從此扣掉 ——
`|median| > clock_max_offset` (差得離譜), **或 `median > clock_future_tol`
(時戳持續落在未來)**。

> 第二個條件比第一個重要, 而且**跟差多少無關**: 真正的延遲只會讓時戳**變舊**,
> 不會讓它變新。所以「持續比濾波器新」本身就是時鐘不對的證明 —— 差 0.5 秒跟差
> 625 秒是同一件事。上表 0.5 秒那一列就是這個規則的價值 (19.33 -> 4.08 cm)。

**(b) 緩衝區的過期判斷用絕對值, 而且加上筆數上限。** 就算時鐘判斷再出什麼錯,
緩衝區也不會無限長大 —— 這是那個「同一筆被算幾百次」的直接死因。

> ⚠️ **偵測救得回「不要壞掉」, 救不回精度。** 時鐘一偏, 真正的延遲就**沒有辦法
> 從資料裡分離出來** —— 扣掉偏移之後每一則量測看起來都像「剛剛才發生」, 延遲
> 補償等於沒有 (上表 625 秒那一列是 7.73 cm, 不是 1.35 cm)。
> 要拿回那 `v x delay`, **只能去源頭把時鐘修好**, 或用 `camera_extra_delay`
> 把量出來的常數延遲手動加回去。status 那行會印 `時鐘+625.5s`。

## [C][E] 少一個來源不是「變不準」, 是「還在跑」

相機被擋住 (柱子後面 / YOLO 漏偵測) 10 秒:

| | 遮蔽期間的位置 RMS |
| --- | --- |
| 只有相機 (拿最新一則) | **174 cm** |
| 融合 (相機 + LiDAR + 遞推) | **1.50 cm** |
| 融合但沒有 LiDAR (只剩遞推撐著) | 4.08 cm |

**相機那條路的可用性由「中斷」決定, 不是由平均誤差。** 這是融合最直接的價值。

絕對量測**全部**掉線 30 秒:

| | 位置 RMS |
| --- | --- |
| 掉線前 | 1.22 cm |
| 掉線中 (等於純航位推算) | 4.02 cm |
| 回來後 1 秒 | 1.72 cm |
| 回來後 | 1.38 cm |

掉線期間 `sigma` 會跟著長大, 所以下游 (nav、`collect_data_node`) 靠它就知道這段
不可信 —— 不需要另外發一個「我掉線了」的訊息。

## [D] 來源自己會知道自己追丟了 —— 用它回報的 sigma 擋

`car_loc_lidar` 在長方形房間裡會鎖到 180 度的對稱解, 鎖住之後**位置看起來還
合理、殘差也很漂亮, 但回不來**。`collect_data_node` 記了實測值:

    正常 sigma ~0.0015,  追丟 ~0.0145    (門檻 0.0025, 三輪資料 0 漏網)

LiDAR 鎖住 15 秒, 位置 RMS:

| | 有 sigma 閘門 | 沒有 |
| --- | --- | --- |
| 相機也在 (兩個來源) | 1.31 cm | 1.31 cm (卡方閘門擋掉 159 則) |
| **只有 LiDAR** | **2.80 cm** | **338 cm** (逃生口強制接受 232 次) |

兩個來源都在的時候卡方閘門一個人就夠 —— 相機一直在提供正確的位置, 鎖住的
LiDAR 跟它差 10 公尺, NIS 破表。**只有 LiDAR 的時候就完全不一樣**: 鎖住之後那些
量測**彼此一致**, 閘門連續擋幾秒就會觸發逃生口, 然後估計整個被搬到鏡射的位置。

> **不要因為「兩個來源時看不出差別」就拿掉它** —— 相機**會**被擋住 ([C]),
> 那時就是「只有 LiDAR」的情況。

**這道閘門在真資料上驗證過了。** 2026-09-10 那一輪 (194 秒) LiDAR 從第 80 秒
鎖到 180 度之後**再也沒有回來** (整段 66% 的量測是鎖住的, 車子自旋到 14 rad/s,
遠超過 8 rad/s 的追蹤上限)。依 `lid_sigma` 分組:

| | n | 位置誤差中位 | yaw 誤差中位 | 其中鎖住 |
| --- | --- | --- | --- | --- |
| sigma < 0.0025 (融合會採用) | 992 | **4.4 cm** | **0.7°** | **0%** |
| sigma > 0.0025 (被閘門擋掉) | 3264 | 256.9 cm | 177.7° | 86% |

**完全分乾淨**, 而且門檻 0.0025 是三個月前在別一輪資料上訂的。

## [F] 濾波器自己也會錯 —— 逃生口

卡方閘門是拿量測跟**濾波器自己的信念**比, 所以它對「P 很小但**是錯的**」完全
沒有辦法。最乾淨的例子是**綁架**: 車子被瞬間搬走 3 m, IMU 與輪速**看不到**這
件事 (它們量的是運動不是位置), 於是濾波器對自己非常有信心, 而每一則正確的絕對
量測都被擋掉:

| | 綁架後 2 秒起的 RMS | 收斂回 20 cm |
| --- | --- | --- |
| 有逃生口 (`abs_reject_time: 3.0`) | 74 cm | **5.0 秒** |
| 沒有 | 337 cm | **永遠回不來** |

機制: 連續 `abs_reject_time` 秒沒有任何絕對量測通過閘門 -> 進入**恢復模式**,
強制接受 (R 放大 9 倍 = 走過去而不是跳過去), 直到有一則自己通過為止。

**一次強制接受不夠** —— 單次修正被 `abs_max_correction` (1 m) 綁住, 而它要處理
的情況動輒好幾公尺。所以是「模式」不是「一次」。

這跟 `car_loc_wheel` 的 `wheel_reject_time`、`car_loc_camera` 的
`force_accept_after` 是同一個病的三個版本: **一次離群是量測的問題, 連續好幾秒
都對不上就是濾波器自己錯了。**

> 節點掉線 10 秒之後回來也會走到這裡 (`test_node.py [4]`): 漂了 61 cm 而 sigma
> 只長到 7 cm, 量測一回來還是被擋, 靠逃生口救回來。
> **「掉線久了 P 自己會長到夠大」在這個時間尺度上不成立** —— P 靠過程雜訊長,
> 誤差靠尺度誤差 x 距離長, 後者快得多。

## [G] 不要把已經濾波過的輸出當成獨立量測

相機發的是**卡爾曼濾波之後**的位置, 連續兩則的誤差是**相關**的; EKF 的更新式
假設每一筆量測的誤差互相獨立。全速吃進來等於把同一份資訊算了好幾次, P 被壓到
比真實精度樂觀 —— 而過度自信的濾波器接下來就會開始擋掉正確的量測 ([D]/[F] 的
防線全部建立在「P 是誠實的」上面)。

判斷的指標是 **NEES** (誤差用濾波器自己報的 P 正規化), 2 自由度的理想值是 **2.0**:

| | 位置 RMS | NEES | 閘門擋掉 |
| --- | --- | --- | --- |
| 全吃 30 Hz, R 不放大 | 1.46 cm | 2.80 | 28 |
| **全吃 30 Hz, R x1.5 (預設)** | **1.35 cm** | **2.26** | 11 |
| 限流到 10 Hz + R x1.5 | 1.44 cm | 2.62 | 10 |
| 限流到 10 Hz + R x2.5 | 1.61 cm | 2.84 | 11 |

**量出來跟原本想的不一樣。** 原本準備用 `min_dt` 限流 (「30 Hz 的相關量測只該
算 10 Hz」), 但限流之後 NEES 反而**變差** —— 兩次更新之間 P 長回來的速度追不上
誤差長大的速度, 少吃的那幾則補不回來。所以 **`camera_min_dt` 預設是 0**,
R 放大一項就夠了 (功能留著: 真車上如果來源的平滑比模擬更重再打開)。

重點是**判斷的方式**: 看 NEES 跟擋掉的數量, 不是只看 RMS。過度自信的濾波器在
乾淨資料上 RMS 更好看, 代價是遇到離群值時完全沒有防禦。

## 三道防線的分工 (每一道擋的東西不一樣)

| | 擋什麼 | 依據 | 為什麼別的擋不到 |
| --- | --- | --- | --- |
| **來源 sigma** (`sources.py`) | 來源**自己知道**這一幀不準 | 它回報的共變異數 | 不看濾波器狀態 —— 鎖住的量測彼此一致時, 卡方閘門反而會被說服 |
| **卡方閘門** | 跟目前信念差太多的量測 | NIS | 對「來源一致地錯」沒轍 |
| **逃生口** | **濾波器自己**錯了 | 連續擋掉的**時間** | 前兩道都預設濾波器是對的 |
| `abs_max_correction` | 單次修正搬太遠 | 絕對上限 (m) | 卡方閘門對「合理但巨大」的修正沒意見 |

## 輸出

| topic | 內容 |
| --- | --- |
| `/fusion_loc/odom` | 位姿 + 速度 + 共變異數 (主要輸出) |
| `/fusion_loc/pose` | `PoseWithCovarianceStamped` |
| TF | `map -> base_link` (`publish_tf:=false` 可關) |
| `~/reset` | `std_srvs/Trigger`: 重新校正零偏, 並用下一則絕對量測當起點 |

`evaluate` 報的是**分布**與**尾巴** (RMS / p95 / 最大), 不是漂移率 —— 融合有絕對
參考, 誤差不隨時間長大。另外三件它會單獨報:

* **常數偏移** —— 不是 0 通常是座標系沒對, 不是定位在漂
* **誤差 vs 車速** —— 跟車速成正比的話就是延遲補償沒做對 ([B])
* **一致性 (誤差 / sigma)** —— 理想 ~1; >2 過度自信, <0.3 過度保守 ([G])

## 出事的時候

| 症狀 | 通常是 |
| --- | --- |
| status 說「還沒有起點, 在等第一則絕對量測」 | 相機/LiDAR 那兩個節點沒開, 或 topic 名字不對。真的不想開就 `wait_for_absolute:=false` + `initial_pose` |
| 誤差跟車速成正比, 靜止時很準 | 延遲補償沒生效。看 status 的「倒帶」次數是不是 0, 以及「太舊」是不是一直在長 (`rewind_horizon` 太小) |
| status 的「太舊」一直增加 | 絕對量測的延遲超過 `rewind_horizon`。調大它 (代價只有記憶體與 CPU) |
| 閘門擋掉的數量很大, 但位置看起來還行 | 遞推那一路跟絕對量測一直在吵架。最常見是 `forward_deg` 給錯, 或 `gravity_mode=complementary` 配了小的 `sigma_acc` |
| 一直在「恢復模式」 | 某個來源持續給錯的位置。先看 `lidar_sigma_max` 有沒有開 ([D]), 再看兩條路線的地圖原點是不是差一個平移 |
| 位置比只用相機還差 | `rewind:=false`, 或 `abs_max_correction` 設太小 (絕對量測拉不動遞推) |
| 誤差是一個不會變的常數 | 座標系沒對: LiDAR 地圖原點是按 Play 那一刻的位置, 相機校正的原點是單應性的原點。`evaluate` 會把常數偏移單獨報出來 |
| 輸出中斷 | `/imu` 沒來。絕對量測斷了不該讓輸出斷 —— 那是遞推的工作 |
| **估計凍結在起點, sigma 小得離譜 (< 1 mm)** | 某個來源的時鐘跟 `/imu` 不同基準 ([H])。看啟動時的紅色警告與 status 的 `時鐘+xxx s`。舊版沒有這道偵測, 症狀就是這個 |
| status 的「未來」不是 0 | 時戳落在濾波器前面。偶爾幾筆是正常的 (量測比最後一則 IMU 新幾毫秒); 一直在長就是時鐘沒對好 |
| 誤差跟車速成正比, 但「倒帶」次數正常 | 來源的時戳本身就晚於真正的量測時刻。拿 CSV 掃 `delay` 找最小值 (2026-09-10 那一輪相機是 +50 ms), 填回該來源的校正檔, 或先用 `<來源>_extra_delay` |
